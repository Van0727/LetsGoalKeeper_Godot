## 1. 迁移结论

这个项目适合重写，不适合自动转换。

Unity 场景、Prefab、ScriptableObject、MonoBehaviour、Addressables、DOTween 和 Unity Spine 组件都不能直接变成 Godot 工程。真正值得保留的是：

- PNG、JPG、字体、音频等原始资源；
- 角色动画源文件先归档保留，暂不纳入本轮迁移；后续如果需要，优先评估 PNG 帧动画；
- 已确认的玩法规则和数值；
- 卡牌、敌人、战利品的名称、描述和配置；
- 旧 C# 代码中的业务逻辑，作为行为参考；
- 原 Unity 项目，作为迁移期间的对照版本。

建议采用“垂直切片”路线：先完成一场可玩的战斗，再加入地图和奖励，最后补齐三章内容与平台功能。不要先把所有类、场景、数据全部搬完。

## 2. 项目审计摘要

### 2.1 已识别的主要系统

| 系统 | Unity 现状 | Godot 处理方式 |
| --- | --- | --- |
| 启动与场景切换 | Boot、Main、Map、多个 Room 场景 | 重建为 Boot、MainMenu、Run、Map、Battle、RestRoom |
| 卡牌 | CardDataSO + 多种 Effect SO | 自定义 `Resource` + 效果执行器 |
| 牌堆 | 抽牌、弃牌、手牌、回合弃牌 | 独立纯逻辑 `DeckState` |
| 战斗 | 多个 Manager + EventSO 通信 | `BattleController` 状态机 + Godot signal |
| 玩家/敌人 | MonoBehaviour + SO 数据 | 固定定义 Resource + 运行时实例状态 |
| 敌人行动 | 行动资源与特殊敌人脚本 | 数据驱动行动 + 少量特殊被动脚本 |
| 连击/主动技 | ActiveSkillManager | `ComboState` + `SkillResolver` |
| 地图 | MapGenerator + Room Prefab | 地图数据模型 + 独立地图 UI |
| 奖励/战利品 | LibrarySO + ItemEffect | 奖励池 Resource + RunState 持有列表 |
| 动画表现 | DOTween、Animator | 本轮不迁移；用静态图和即时反馈占位 |
| 事件系统 | ScriptableObject Event | signal / EventBus，仅跨场景事件使用总线 |
| 动态资源加载 | Addressables | `preload/load` + Resource 路径或资源注册表 |
| Spine | spine-unity | 不迁移运行库；保留源资源，后续可改为 SpriteFrames 帧动画 |
| UI | Unity UI、UI Toolkit/UXML | Godot Control + Theme + Container |

### 2.2 不迁移的内容

- `Library`、`Temp`、`Logs`、Unity 缓存；
- `.meta` 文件；
- Unity 自带包、TextMesh Pro、Unity Shader；
- `Spine/Runtime` 目录中的 Unity/C# 运行库；
- DOTween 和其他仅供 Unity 编辑器使用的插件；
- Addressables 的组、构建脚本和缓存；
- Unity `.unity`、`.prefab` 的序列化内容本身；
- 已知错误、测试占位数据和直接修改 ScriptableObject 的做法。

## 3. 先冻结 Unity 原型

迁移期间保留两个独立目录：

```text
LetsGoalKeeper_Unity/     # 只用于运行、截图、查行为，不再开发新功能

```

冻结前完成：

- [ ] Unity 项目能打开并运行；

- [ ] 对每张卡、每个敌人、每件战利品截图或录屏；
- [ ] 导出所有关键数值到表格或 Markdown；
- [ ] 保存 5～10 个典型战斗结算例子；
- [ ] Git 创建迁移前标签，例如 `unity-final-reference`；
- [ ] Unity 版只修阻碍对照测试的严重错误，不再增加功能。

## 4. 开发前需要先拍板的规则

以下值不能照抄 Unity，因为原工程互相冲突或仍是占位：

| 问题 | 首版建议 | 后续能否改数据解决 |
| --- | --- | --- |
| 每回合能量 | 3 | 能 |
| 初始牌库 | 攻击×4、防御×2、能力×2，可再调整 | 能 |
| 手牌抽取 | 回合开始抽3；出牌后补1 | 能 |
| 玩家护盾清零 | 玩家回合开始清零 | 能 |
| 敌人护盾清零 | 敌人回合开始清零 | 能 |
| Buff持续时间扣除 | 受影响角色完成自己的回合后扣1 | 能 |
| 力量/虚弱叠加 | 倍率不叠加，只刷新或增加持续回合 | 能 |
| 战斗奖励 | 卡牌和战利品各选1个 | 能 |
| 第三章 Boss | 独立通关结算，不触发失败 | 需要流程代码 |
| 第2章精英池 | 未补数据前不生成精英房 | 能 |

若暂时不想决定，按“首版建议”实现，所有数值放进 Resource，之后无需改核心代码。

```text

  battle/

```

### 核心原则

1. Resource 只存固定定义，不存玩家当前血量、是否拥有等运行状态。
2. 战斗规则和画面分开：本轮不建设动画系统，数值结算不能依赖动画完成回调。
3. 不建立十几个全局 Manager；首版 Autoload 控制在 3～4 个。
4. 节点之间优先使用直属引用和 signal，只有跨场景通知才使用 EventBus。
5. 每个功能完成后立即做最小测试，不攒到最后一起调试。

## 6. 数据模型设计

### 6.1 固定定义 Resource

建议建立：

- `CardDefinition`：ID、名称、费用、类型、射门类型、图片、效果数组、稀有度；
- `EffectDefinition`：效果类型、基础值、次数、目标、附加参数；
- `EnemyDefinition`：ID、最大生命、场景、行动表、被动ID；
- `EnemyActionDefinition`：行动类型、数值、权重、效果数组；
- `ItemDefinition`：ID、描述、稀有度、效果数组；
- `SkillDefinition`：类型、基础值、表现资源占位、效果数组；
- `MapConfig`：层数、每层房间数、房间权重、Boss；
- `EncounterPool`：章节、房型、可选敌人及权重。

所有定义使用稳定英文 ID，例如 `card_banana_shot`。中文名称只是显示文本，不能作为存档键或代码判断条件。

### 6.2 本局运行状态

`RunState` 至少保存：

```text
seed
chapter
player_hp / max_hp
deck_card_ids
owned_item_ids
damage_modifiers
map_state
current_room_id
```

战斗临时状态只在 `BattleState` 中保存：

```text
player/enemy hp、shield、energy、buffs
draw_pile、discard_pile、hand
turn_phase
enemy_action_index
combo_type、combo_count
当前随机数状态
```

离开战斗时，只把应该跨房间保留的数据写回 `RunState`。

## 7. 逐阶段实施计划

工期按“个人、代码基础一般、AI 辅助、每周约 15～20 小时”估算。本计划不包含正式角色动画制作，实际时间主要取决于 UI 还原和内容补齐程度。

### 阶段 0：工程、输入与资产试验（2～4天）

目标：先证明最危险的资源能在 Godot 使用。

任务：

- [ ] 安装一个明确版本的 Godot 4.x，并固定版本；
- [ ] 新建空项目和 Git 仓库，添加 Godot `.gitignore`；
- [ ] 设定基准分辨率、拉伸模式和手机安全区策略；
- [ ] 导入1张背景、1张卡图、1个字体，确认中文显示；
- [ ] 做一个鼠标与触摸都能拖拽的卡片样例；
- [ ] 用静态角色图建立玩家和敌人占位节点；
- [ ] 将 Spine 等动画源文件单独归档，不把 Unity 动画运行库复制进新工程；
- [ ] 在 Windows 导出一个空测试包；
- [ ] 在一台 Android 真机安装测试包。

验收：同一个测试场景能在 Windows 和 Android 打开，静态角色正常显示，卡牌可拖动。

本阶段无需确定最终动画技术。正式动画作为后续独立项目，不阻塞玩法迁移。

### 阶段 1：纯战斗逻辑骨架（5～7天）

目标：不用正式 UI 和动画，先跑通确定性的战斗规则。

任务：

- [ ] 建立 `CombatantState`；
- [ ] 实现伤害、护盾、治疗、能量；
- [ ] 建立 `BattleController` 回合状态机；
- [ ] 定义阶段：初始化、玩家开始、玩家操作、玩家结束、敌人行动、结算；
- [ ] 实现 Buff/Debuff 与持续回合；
- [ ] 实现固定随机种子；
- [ ] 用文本日志显示所有结算步骤；
- [ ] 为伤害、护盾、治疗、死亡写最小自动测试。

验收：点击测试按钮即可完成数个回合；相同 seed 得到相同结果；无画面也能判断胜负。

### 阶段 2：卡牌、牌堆与效果系统（7～10天）

目标：打牌闭环成立，并能靠新增数据扩展卡牌。

迁移顺序：

1. 直球：单次伤害；
2. 手套：护盾；
3. 佳得乐：治疗；
4. 毛巾：恢复能量；
5. 香蕉球、挑射：不同射门类型；
6. 一组射门、双向香蕉球：多段伤害；
7. 嗜血球、尖刺球：多效果顺序；
8. 爆炸球：概率分支和中断；
9. 能量射门：读取剩余能量；
10. 助跑、虚弱：状态效果。

任务：

- [ ] 建立 `CardDefinition`、`EffectDefinition`；
- [ ] 实现抽牌堆、弃牌堆、手牌、洗牌；
- [ ] 实现费用检查和支付；
- [ ] 实现“出牌后补1张”；
- [ ] 实现回合结束弃掉剩余手牌；
- [ ] `EffectResolver` 按数组顺序执行效果；
- [ ] 支持效果中断后续结算；
- [ ] 卡牌运行实例不修改定义 Resource。

验收：当前17张卡牌都能由数据生成；除特殊机制外，不为每张卡写独立脚本。

### 阶段 3：战斗界面与统一输入（5～8天）

目标：做出首个真正可玩的战斗切片。

任务：

- [ ] 玩家、敌人、血条、护盾、能量、意图 UI；
- [ ] 卡牌扇形或横向布局；
- [ ] 鼠标/触摸统一拖拽接口；
- [ ] 有效出牌区高亮和无效回弹；
- [ ] 卡牌结算期间锁定重复输入；
- [ ] 直球、香蕉球、挑射、随机射门暂时只显示类型图标或文字；
- [ ] 足球暂用静态图瞬移或简单显隐占位，不建设正式动画系统；
- [ ] 受击、治疗、护盾先用数值变化和颜色闪烁反馈；
- [ ] 结束回合按钮；
- [ ] 胜利、失败界面。

验收：Windows 鼠标和 Android 触摸都能完整打完一场战斗，不出现重复出牌或结算卡死。

### 阶段 4：敌人、行动意图与特殊被动（5～8天）

目标：迁移普通、精英、Boss 的可配置行为。

任务：

- [ ] 数据驱动攻击、防御、治疗、虚弱行动；
- [ ] 普通/精英按行动列表循环；
- [ ] Boss 按权重或随机选择行动；
- [ ] 意图显示最终随机后的值；
- [ ] 熊：主动技伤害减半；
- [ ] 乌龟：受击反伤1；
- [ ] 企鹅及其他特殊组合效果；
- [ ] 配置章节遭遇池；
- [ ] 补齐或禁用生命为6的占位敌人；
- [ ] 空敌人池时给出明确错误，不让游戏崩溃。

验收：至少1个普通、1个精英、1个Boss可正常完成战斗；更换敌人主要改数据。

### 阶段 5：连击和三个主动技能（3～5天）

目标：恢复游戏的核心差异化机制。

任务：

- [ ] 同类型卡连续使用时累积连击；
- [ ] 换类型后重置为1；
- [ ] 3点起技能按钮可用；
- [ ] 超级攻击、超级防御、超级能力分别配置；
- [ ] 使用技能后清空类型与点数；
- [ ] 主动技伤害打上独立标签，供熊的减伤判断；
- [ ] 进新房间清空连击。

验收：三个技能类型都能正确触发，UI 状态和数值一致；正式动画不在本阶段验收。

> 至此形成 Milestone A：单场战斗 Demo。完成前不做地图和完整三章。

### 阶段 6：本局状态、奖励与战利品（7～10天）

目标：战斗结果能影响后续战斗。

任务：

- [ ] 建立 `RunState`；
- [ ] 新游戏初始化生命、牌库、章节和 seed；
- [ ] 普通/Boss 卡牌奖励池；
- [ ] 三选一卡牌；
- [ ] 三选一战利品；
- [ ] 已拥有战利品排重；
- [ ] 全伤、直球、香蕉球、挑射加成；
- [ ] 角旗杆暂时禁用，或先补角球卡；
- [ ] 奖励加入 RunState 后下一战生效；
- [ ] 新游戏不会残留上局数据。

验收：连续打两场时，第一场获得的卡牌和战利品能在第二场正确生效。

### 阶段 7：路线地图和房间流程（7～10天）

目标：形成完整 Roguelike 循环。

任务：

- [ ] 地图数据生成与地图画面分离；
- [ ] 三层地图以及 2～3、2～3、1 个房间；
- [ ] 确保每个房间有下一层连线、下一层均可达；
- [ ] Locked、Attainable、Visited 三状态；
- [ ] 进入一个房间后锁定同层其他路线；
- [ ] 普通、精英、Boss 房；
- [ ] 休息房和20点治疗；
- [ ] 房间结束回地图并更新状态；
- [ ] 保存地图的节点、连线与状态，不只保存随机 seed。

验收：玩家不能进入非法房间；退出并继续后地图不重新随机。

### 阶段 8：章节、完整内容和结局（7～14天）

目标：把原型内容补成完整三章。

任务：

- [ ] 第一章敌人池、Boss 和背景；
- [ ] 第二章补精英池或调整地图权重；
- [ ] 第三章内容；
- [ ] Boss 后章节递增并重新生成地图；
- [ ] 第三章 Boss 后进入独立通关界面；
- [ ] 死亡进入失败界面；
- [ ] 主菜单、开始新游戏、继续游戏；
- [ ] 内容缺失时用显眼的开发占位提示，而不是静默失败。

验收：能从新游戏完整玩到第三章通关，也能正常失败并重开。

> 至此形成 Milestone B：PC 内容完整 Alpha。

### 阶段 9：存档、设置和健壮性（5～8天）

目标：达到可以交给外部玩家测试的程度。

任务：

- [x] JSON 或 Godot Resource 存档；
- [x] 存档版本号与迁移入口；
- [x] 原子写入：先写临时文件，成功后替换正式存档；
- [x] 自动保存节点：进房前、战斗胜利后、选奖励后、章节切换后；
- [x] 音量、语言、窗口/全屏设置；语言切换框架已接入，完整英文翻译资源留待本地化内容切片；
- [x] 暂停与退出确认；地图、战斗、奖励和休息房共享暂停层，并支持 Esc 与移动端返回键；

目标：在 PC Alpha 稳定后再适配手机，不与核心重写并行。

任务：

## 9. 资源迁移清单

### 可直接尝试导入

- PNG、JPG：导入后逐项设置 Filter、压缩和像素密度；
- TTF/OTF：检查中文字符授权与显示；
- WAV/OGG/MP3：按 BGM、UI、SFX 分音频总线；
- Spine 源数据：仅归档，不导入本轮运行工程；后续可据此导出 PNG 序列帧；
- JSON/CSV：可作为一次性数据转换源。

### 需要重建

- 所有 `.tscn` 场景；
- Control UI 布局和 Theme；
- Tween、Animator 状态机（本轮不重建）；
- Unity Shader/Shader Graph；
- ParticleSystem；
- Prefab 引用关系；
- ScriptableObject 数据资产；
- Addressables 加载流程。

### PSD 的处理

PSD 不应直接作为运行资源。保留它作为源文件，并导出清晰命名的 PNG。若 PSD 含切片或层级动画，先整理图层命名再批量导出。

## 10. Unity → Godot 概念对照

| Unity | Godot |
| --- | --- |
| GameObject / Component | Node / 子节点 / Script |
| Scene / Prefab | PackedScene (`.tscn`) |
| MonoBehaviour | 继承 Node/Control/Node2D 的 GDScript |
| ScriptableObject | Resource |
| UnityEvent / EventSO | signal / Callable / EventBus |
| Coroutine | `await` signal / SceneTreeTimer |
| DOTween | Tween |
| Animator | AnimationPlayer / AnimationTree |
| RectTransform | Control + Container + Anchor |
| SpriteRenderer | Sprite2D |
| Canvas | CanvasLayer / Control |
| Addressables | ResourceLoader / preload / 自建注册表 |
| PlayerPrefs | ConfigFile 或自建存档 |

## 11. AI 协助开发的正确拆法

不要对 AI 说“把整个 Unity 项目转换成 Godot”。每次只提交一个可验证模块。

### 每个任务的标准输入

1. 当前阶段目标；
2. 对应的玩法规则；
3. 旧 Unity 的相关脚本，不要发送整个 Assets；
4. 当前 Godot 文件树和相关脚本；
5. 明确输入、输出、边界情况；
6. 验收步骤；
7. 限制：不修改哪些文件、不新增哪些架构。

### 推荐任务模板

```text
当前在做阶段2：牌堆系统。
请基于附带的玩法规则，在 Godot 4.x + GDScript 中实现 DeckState。

规则：
- 战斗开始复制本局牌库并洗牌；
- 回合开始抽3张；
- 出牌后补1张；
- 抽牌堆为空时将弃牌堆洗回；
- 回合结束弃掉剩余手牌。

要求：
- 纯逻辑类，不操作 UI 节点；
- 固定 seed 时结果可复现；
- 不修改 CardDefinition Resource；
- 给出变更文件、测试场景和人工验收步骤；
- 只完成本任务，不顺手创建地图、存档或全局管理器。
```

### 每次让 AI 完成后的检查

- [ ] Godot 能无报错启动；
- [ ] 查看 AI 实际修改了哪些文件；
- [ ] 核心规则至少手测一次；
- [ ] 提交一次 Git；
- [ ] Commit 只包含一个功能；
- [ ] 更新迁移清单；
- [ ] 不理解的代码先让 AI 解释，再继续叠功能。

## 13. 测试矩阵

### 战斗规则测试

- 伤害小于、等于、大于护盾；
- 治疗不超过最大生命；
- 能量不足不能出牌；
- 抽牌堆为空时正确洗回；
- 多段攻击中途杀死敌人后停止后续不合理表现；
- 自伤导致玩家死亡；
- 爆炸球成功与失败两个分支；
- 力量和虚弱持续回合；
- 主动技能与熊减伤；
- 乌龟反伤导致双方同时死亡时的裁定。

### 流程测试

- 普通、精英、Boss 胜利；
- 玩家失败；
- 奖励池不足3个时；
- 战利品全部持有时；
- 第2章精英池为空时；
- 第三章 Boss 通关；
- 中途退出并继续；
- 新游戏彻底清空旧局。

| 安全区 | 可选 | 必测 | 必测 |
| 暂停恢复 | 必测 | 必测 | 必测 |
| 存档路径 | 必测 | 必测 | 必测 |
| 多分辨率 | 必测 | 必测 | 必测 |

## 14. 主要风险与应对

| 风险 | 严重度 | 处理 |
| --- | --- | --- |
| 后续帧动画接入影响战斗代码 | 中 | 战斗结算不等待动画；表现层只监听结算事件 |
| AI 一次改动过大，代码逐渐不可控 | 高 | 单功能任务、小提交、每次验收 |
| Resource 被当运行状态修改 | 高 | 定义与实例分离，自动测试 |
| PC 完成后才发现触摸架构不支持 | 高 | 阶段0和阶段3就统一输入 |
| Unity 数值本身存在冲突 | 中 | 以玩法基准文档为准，做决策表 |
| 为“架构漂亮”过度设计 | 中 | 先垂直切片，只抽象已经重复的逻辑 |
| 同时做 Steam、Android、iOS 导致进度分散 | 中 | Windows基准版稳定后再做手机 |
| 原美术授权只允许 Unity 使用 | 高 | 核查 Asset Store、字体及第三方素材的跨引擎授权 |
