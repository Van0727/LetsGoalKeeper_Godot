# LetsGoalKeeper：Demo 之后的开发路线

> 2026-09-09｜目标：手机 + Steam 的单人独立游戏。依据当前代码静态检查；未运行 Godot 或真机测试。以下体量与验收数字是规划起点，不是市场结论或工期承诺。

## 1. 先确定游戏最值得放大的特点

**让玩家用卡组安排足球攻防，再用节奏把战术打出来。** 自己觉得 Demo 有趣是好信号，下一步先验证陌生玩家是否也愿意反复玩，再全力铺量。

创新优先围绕已有足球、连击和拍数系统，每次只验证一项：

| 方向 | 最小玩法例子 | 优先级 / 成本 |
| --- | --- | --- |
| 乐句战术 | 攻击→防御→攻击完成一次“配合”，末张准拍获得额外收益；思考时不计时，主动开启乐句后才要求连续拍点 | 首选 / 中；与现有同类连击比较，避免两套规则争夺注意力 |
| 守门员节奏个性 | 敌人预告下一轮强拍封堵；玩家选择弱拍射门或换用防守牌 | 首选 / 中；先做一个敌人，清楚显示合法拍点 |
| 准拍扑救 | 结束回合准拍获得一次防守奖励 | 候选 / 低至中；若每回合都必按，容易变成机械作业；避免免费免伤挤掉防御牌 |
| 卡组参与编曲 | 攻击、防御、能力牌分别触发短音色，连击叠加乐器层 | 后续 / 中至高；先做音色反馈，再考虑同步分轨 |
| 曲风构筑 | 稳拍流累积资源，爆发流主动选择短乐句连续出牌 | 后续 / 高；先用少量卡证明差异，不做整套曲风克制表 |

首轮只选一个主创新，配一个反馈增强。自由思考与限时演奏必须明确分开，不能逼玩家边读长文本边赶拍。

对比当前“Miss 半伤”与“基础效果保留、准拍额外奖励”两版。记录等待拍点的时间、失败原因和重玩意愿；不要只看 Perfect 比例。

## 2. 底层已有基础，重点补齐这些缺口

已有：独立节拍时钟、战斗控制器与效果执行器、固定种子、地图奖励、版本化安全节点存档、诊断日志、卡牌 CSV 导入及冒烟测试。旧玩法文档记录的是 Unity 原型，不能把其中的问题直接当作当前缺陷。

| 优先级 | 当前证据与下一步 |
| --- | --- |
| P0：设备上的公平判定 | `rhythm_clock.gd` 已有校准参数，设置服务尚未保存它。补校准入口、判定难度与弱动态选项；实测扬声器、耳机、低帧率、暂停和长时间循环 |
| P0：结算可靠性 | 战斗界面存在等待音频时间及飞球完成的流程。审查音乐启动失败、停止、退场、多段致死和重复输入时能否结束；这属于待验证风险，尚未确认为故障 |
| P0：手机续玩 | `run_state.gd` 明确不保存战斗手牌与回合。先决定“重开当前战斗”还是“恢复回合边界”；后者需要牌堆、敌人意图、随机数状态等快照及迁移测试 |
| P1：内容生产安全 | 导入器已有整表校验，但逐资源写入可能部分成功。补失败回滚或暂存提交、稳定 ID 与跨资源引用校验，覆盖 `@tool` 依赖和编辑器重启加载 |
| P1：可复现调试 | 固定种子已有；补内容版本、输入顺序和判定结果记录。单独一个种子不足以重现玩家节奏操作 |
| P1：平台与文案 | 当前以 360×640 竖屏为基准。验证手机遮挡、安全区与后台恢复，设计桌面宽屏布局及键鼠操作；语言设置已有不等于所有文本已可翻译 |

暂不建设通用插件框架、复杂谱面编辑器和完整回放系统。后续若改结算取消机制、恢复快照或事件契约，会涉及核心状态机、跨场景数据或存档，应分别提交实施方案。

## 3. 铺量前建立生产规则

**先做一个接近成品的章节，测出真实制作成本，再复制生产。**

- 建“流派 × 功能”矩阵：每个流派都要有启动、收益、防守和补救手段；用奖励池保证有机会成型。
- 每张卡写清用途、费用基准、组合对象和克制场景。攻击牌同时预算伤害与占用拍数，防止多段动画拖长整场战斗。
- 敌人按教学、检验、反制、综合挑战分工；增加新决策比换皮加血更有价值。
- 每批做 5～8 张卡、2 个敌人，跑完一局再继续；检查选择率、弃选原因、过强组合和重复感。
- 音乐记录 BPM、首拍、循环边界、授权凭证和音量基准；普通敌人优先共享章节音乐，精英与 Boss 做变体。
- 统一资源命名、稳定 ID、文本键和美术尺寸；删改内容时明确旧档如何处理。

首发预算可先设为：**1 个角色、3 个构筑方向、40～60 张卡、15～25 件战利品、3 章、每章 3～4 种普通敌人及各 1 种精英/Boss**。先只生产样板章节；其余数量按重玩反馈增减。联机、多个角色和每日挑战延后。

建议先按买断制设计核心体验；手机是否采用试玩后解锁，单独验证。尽早确定 Android/iOS 范围和目标设备，保持双端可运行；发售顺序可错开，减少同时发布压力。

## 4. 接下来每个阶段做什么

按完成条件推进；做完样板章节后，再根据每项内容的实际耗时估算工期。

| 阶段 | 主要工作与产物 | 完成条件 |
| --- | --- | --- |
| ① 核心验证 | 选一个创新；对比节奏奖惩；找 6～10 位陌生玩家，包含非音游玩家 | 多数能独立完成战斗并解释判定；记录主动重玩和退出原因，解决共同卡点 |
| ② 完整样板章节 | 约 12～18 张卡、2 种可成型构筑、3 普通敌人、1 精英、1 Boss；补教程、音乐与成品 UI | 玩家不靠口头指导完成章节；两种构筑都能通关；手机和桌面完整跑通 |
| ③ 底层收口 | 补 P0/P1、续玩策略、数据校验和导出流程；冻结内容格式 | 正常、边界、失败路径通过；旧档、坏数据、暂停恢复有明确结果 |
| ④ 分批铺量 | 按矩阵补三章，逐批接入卡牌、敌人、战利品、美术与音乐 | 三章闭环；无占位效果；各流派能成型，无明显必选卡和无解敌人 |
| ⑤ 测试与打磨 | 外部试玩、数值回归、真机性能、文本及无障碍；停止加系统 | 无已知阻断流程或丢档问题；连续多局及设备矩阵通过，目标帧率稳定 |
| ⑥ 发售准备 | 商店页、实机视频、公开 Demo、平台构建与审核、反馈和热修复流程 | 安装、购买流程、存档升级及发布包完成验收；提交审核前留出返工时间 |

商店素材与曝光从②开始并行，不必等内容全部做完。Steam 官方支持通过 Coming Soon 页面积累愿望单；提前发布 Demo 时，需要准备正式游戏商店页，见 [Steam Demo 文档](https://partner.steamgames.com/doc/store/application/demos)。

手机后台可能伴随进程回收，续玩验收不能只测暂停按钮，见 [Android 生命周期文档](https://developer.android.com/guide/components/activities/activity-lifecycle)。iOS 范围确定后另查对应官方要求。

## 5. 下一轮直接执行的清单

1. 写一页体验目标：核心创新、目标单局时长、首发平台、首发范围上限。
2. 给外部玩家当前 Demo，记录看牌、等待、出牌与退出位置。
3. 根据反馈选择一个创新实验，同时优先补影响测试可信度的校准问题。
4. 先打磨样板章节；未证明重玩价值前，暂停大规模新增内容。

验收时先运行相关 `tests/smoke_*.gd`，再用正式速度人工测试：普通出牌、多段致死、暂停跨拍、循环接缝、音乐加载失败、切后台后终止并重启、损坏存档与导入写入失败。测试使用隔离存档和数据目录；高速冒烟测试不能替代真实音频同步及真机验证。本次仅整理文档，以上验证尚未执行。
